# Plan: UI Message Bridge Refactoring (SimpleMessage vs UiCommand)

## 1. Context

Trennung von Chat-Content (`SimpleMessage`) und Steuerimpulsen (`UiCommand`-Hierarchie) in der Java-zu-HTML Brücke.
Aktuell werden beide über ad-hoc `LinkedHashMap` Instanzen serialisiert — die neuen Typen bringen Struktur und Typsicherheit auf Java-Seite.

Die `role` vs `type` Diskriminierung im JSON bleibt erhalten: Chat-Content hat `role`, Commands haben `type`.

## 2. Design Decisions

- **Trennung via `role` vs `type` bleibt** — kein gemeinsames Interface. SimpleMessage ist Domain-Daten, UiCommand ist Control-Plane.
- **`sealed interface UiCommand`** mit record-Implementierungen — modern, exhaustiv, kompakt.
- **`postMessage(Object)`** — akzeptiert SimpleMessage oder UiCommand. Jackson serialisiert beides korrekt.
- **DIFF als `SimpleMessage.Type.DIFF`** — Diffs sind Chat-Content (bleiben im Message-Stream), kein Steuerimpuls.
- **Kein `@JsonTypeInfo`** — records serialisieren Methoden (`type()`) automatisch als JSON-Feld.

## 3. Architecture Decisions

- Klassen landen in **`org.sterl.llmpeon.parts.widget.model`** (Plugin-Project) — sie sind SWT/Browser-spezifisch, gehören nicht nach core.
- JS-Dispatch: **zuerst `data.type` prüfen, dann `data.role`** — Commands haben höhere Priorität (z.B. Theme-Change vor Message-Render).

## 5. Rules & Constraints

- **Naming:** `UiCommand` ist sealed; Implementierungen sind records mit `type()` Methode.
- **SetThemeCommand:** `static final LIGHT` / `static final DARK`, privater Konstruktor via `record` default.
- **HideLiveStatusCommand:** Singleton-Pattern (record ohne Felder, `static final INSTANCE`).
- **Jackson:** ObjectMapper in ChatMarkdownWidget hat `FAIL_ON_UNKNOWN_PROPERTIES = true` — keine neuen Felder einführen, die nicht serialisiert werden.
- **JS-Dispatch:** `if (data.type) { switch... } else if (data.role) { ... }` — Reihenfolge ist wichtig.
- **DIFF Handling:** `role === 'DIFF'` → `appendDiff(data.message)` (nicht `md.render()`).

## 6. BDD Acceptance

### Scenario: UiCommand serialisiert korrekt mit type-Feld
```
GIVEN eine LiveStatusCommand("thinking...", 30.0, "Analyzing...")
WHEN via Jackson ObjectMapper serialisiert
THEN JSON enthält {"type": "updateLiveResponse", "state": "thinking...", "tokPerSec": 30.0, "chunk": "Analyzing..."}
```

### Scenario: SetThemeCommand LIGHT/DARK Konstanten
```
GIVEN SetThemeCommand.LIGHT
WHEN type() aufgerufen
THEN "setTheme" zurückgegeben
AND theme() "light" zurückgegeben
```

### Scenario: HideLiveStatusCommand ist Singleton
```
GIVEN HideLiveStatusCommand.INSTANCE zweimal referenziert
WHEN beide instanziiert
THEN dieselbe Instanz (==)
AND JSON ist {"type": "hideLiveStatus"}
```

### Scenario: SimpleMessage.DIFF wird im JS als Diff gerendert
```
GIVEN ein MessageEvent mit {role: "DIFF", message: "--- a/foo.java\n+++ b/foo.java\n..."}
WHEN im chat.html dispatcht
THEN appendDiff(message) aufgerufen
AND md.render() NICHT aufgerufen
```

### Scenario: postMessage akzeptiert SimpleMessage und UiCommand
```
GIVEN ChatMarkdownWidget mit ready Browser
WHEN appendMessage(new SimpleMessage(Type.DIFF, "unified diff")) aufgerufen
THEN JSON {role: "DIFF", message: "unified diff"} an Browser gesendet
WHEN showDiff() mit UiCommand ersetzt
THEN gleicher JSON output wie vorher
```

### Scenario: JS-Dispatch Priorität (type vor role)
```
GIVEN ein Payload mit sowohl type ALS AUCH role
WHEN dispatcht
THEN type-Zweig gewinnt (Command priorisiert)
```

### Increment 3: chat.html + test-chat.html Anpassung

**chat.html** JS-Dispatch (~line 340):
```javascript
// Vorher: if (data.role) ... else if (data.type)
// Nachher: type zuerst prüfen
if (event.data.type) {
    switch (event.data.type) {
        case "updateLiveResponse":
            updateLiveResponse(event.data.state, event.data.tokPerSec, event.data.chunk);
            break;
        case "hideLiveStatus":
            hideLiveStatus();
            break;
        case "appendDiff":  // legacy fallback — kann bleiben
            appendDiff(event.data.diff);
            break;
        case "clearMessages":
            clearMessages();
            break;
        case "setTheme":
            setTheme(event.data.theme);
            break;
    }
} else if (event.data.role) {
    if (event.data.role === 'DIFF') {
        appendDiff(event.data.message);
    } else {
        appendMessage(event.data);
    }
}
```

**test-chat.html**:
- `testDiff()` → `send({role: 'DIFF', message: '--- a/...\n+++ b/...\n...'})` statt `type: 'appendDiff'`
- Buttons für Commands bleiben unverändert (schon korrekt mit `type`)
- Optional: Button für `hideLiveStatus` hinzufügen

**Verifikation:** test-chat.html im Browser öffnen, alle Buttons durchklicken.
