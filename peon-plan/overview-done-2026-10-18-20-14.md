## 1. Context — Ziel

Escape-Hatch während laufender Agent: Nachricht mit `!`-Präfix wird **nicht gequeued**, sondern das `!` entfernt und der Text **direkt ins `ThreadSafeMemory`** des aktiven Agenten + sofort in die Chat-History. Kein neuer Turn, kein Follow-up, kein `Noted…`-Echo, kein `(queued …)`-Marker. Beginnt der Rest mit `/`, wird Command/Skill aufgelöst (Body ersetzt den Slash-Anteil, Rest wird angehängt); nicht gefunden → Rohtext. Homepage dokumentiert die Funktion (Regel 8, Punkt 7).

**Pauls Entscheide (nicht verhandeln):**
- **D-idle:** Agent idle → normaler Turn mit dem Text **wie getippt** (das `!` wird NICHT gestrippt).
- **D-compact:** Race Compact-vs-Override wird NICHT gelöst (⏳-Risiko, Paul dokumentiert in der SOLL-Doku). Plan baut KEINE Sonderbehandlung/Queue-Ersatzlogik.

Regel 1–7 und 9 bleiben grün und **unangetastet**.

## 2. Design-Entscheidungen

1. **Neue headless Core-Einheit `OverrideMessageResolver`** (Package `org.sterl.llmpeon.queuedmessages`, neben `UserMessageQueue`):
   reine Entscheidungsfunktion `resolve(String text, boolean agentWorking, CommandService commands, SkillService skills) → Optional<String>` (String = Text für das Memory). Kein Agent-Referenz, kein Memory-Zugriff, keine Queue — dadurch headless testbar. Konstruktionsmuster wie `SlashCommandResolver` (stateless, pro Call `new`).
2. **Slash-Auflösung wird wiederverwendet, nicht neu gebaut:** `SlashCommandResolver.resolve(rest, commands, skills)` (Core, existiert, heute einzige Produktions-Stelle: `AIChatView.java:570`). `OverrideMessageResolver` ist der zweite Konsument (One behaviour, one implementation).
3. **Memory-Write über neue Methode `AiAgent.injectUserMessage(String)`** (Interface-Default = no-op, Override in `AbstractAgent` = `memory.add(UserMessage.from(text))`) — exakt der bestehende Direkt-Schreibpfad wie `handleAbortAndDrain` (`AbstractAgent.java:287`). Die View reicht nur weiter (`active.injectUserMessage(...)`) statt in `getMemory()` hineinzugreifen (Encapsulation; View hat `getMemory()` bisher nur read-only genutzt). Namenscheck: `injectUserMessage` existiert workspace-weit noch nicht (Grep 0 Treffer).
4. **View-Wiring an EXAKT EINER Stelle:** oben in `AIChatView.resolveOutgoingMessage` (vor der Slash-Resolution). Treffer → `injectUserMessage` + `chatHistory.appendMessage(SimpleMessage(Type.USER, resolvedText))` + `chatInput.clearText()` + `chatInput.dismissSlashMenu()` + `return SendDecision.Skip`. Kein `queueMessage`, kein `Noted…`-Echo, kein `updateLiveResponse`, kein `submitAiJob` — keine Duplizierung der Queue-Logik.
5. **Semantik-Abgrenzung zum normalen Slash-Pfad (wichtig):** im normalen Pfad landet der Command-Body im **oneTimeOrder** (User-Context) und nur der Trailing-Text in der Message; beim Override landet **Body + Trailing-Text als ein Text im Memory** (`"instruction content rest text"` laut BDD). Kein oneTimeOrder, keine „Using 🪄:"-History-Zeile.

```mermaid

  subgraph View [AIChatView — verdrahtet nur]

    ROM -->|D1-Guard: „!" + leer| NOOP[clearText, return]
    ROM --> OMR
    ROM -->|Optional.empty| NORM[bestehender Pfad:<br/>Slash → History → isWorking?<br/>Queue+„Noted“ : Skip / Submit]
  end
  subgraph Core [llmpeon-core — headless]
    OMR[OverrideMessageResolver<br/>resolve(text, working, cmd, skill)<br/>→ Optional‹String›]
    OMR -.wiederverwendet.-> SCR[SlashCommandResolver<br/>(bestehend, AIChatView:570 = Site 1)]
    INJ[AiAgent.injectUserMessage<br/>Default no-op]
    ABS[AbstractAgent.injectUserMessage<br/>= memory.add(UserMessage.from(text))<br/>wie handleAbortAndDrain :287]
  end
  OMR -->|Optional.of(resolved)| INJ --> ABS --> MEM[(ThreadSafeMemory<br/>sichtbar für laufenden Turn<br/>beim nächsten Modell-Call)]
  OMR -->|Optional.of| HIST[chatHistory.appendMessage USER]
```

Abhängigkeitsrichtung: View → Core. `OverrideMessageResolver` kennt weder Agent noch Queue noch Memory. Die Queue (`UserMessageQueue`) wird auf dem Override-Pfad **nirgends** berührt.

**Sequenz (Override-Fall):** User sendet `!…` → `doSendMessage` (trim) → `resolveOutgoingMessage` → `OverrideMessageResolver.resolve` (working? `!`? → strip, ggf. Slash) → `present`: `active.injectUserMessage(resolved)` (Memory) + `chatHistory.appendMessage(USER, resolved)` + Input clear → `Skip`. Laufender Turn sieht den Text im nächsten Loop-Schritt (Memory wird pro Iteration neu gelesen) — kein UI-Zutun mehr.

## 5. Regeln & Constraints

- **Regel 1–7 und 9 unverändert**: `UserMessageQueue`, `AbstractAgent.call()`, `handleAbortAndDrain`, Queue-Tests, Rule-9-Tests bleiben grün und unangetastet.
- **D-idle:** idle + `!`-Text → normaler Pfad **mit dem Text wie getippt** (`!` bleibt). Kein Strip.
- **D-compact:** kein Code gegen Compact-Race; Da Mek „fixt" nichts in Richtung Queue-Fallback (das wäre SOLL-Verstoß).
- **Kein Queue-Kontakt** auf dem Override-Pfad: `UserMessageQueue`/`queueMessage`/`drainQueue` dürfen nicht aufgerufen werden.
- **Keine Marker/Echos:** kein `Noted…`, kein `updateLiveResponse`, kein `(queued …)`, kein oneTimeOrder, keine „Using 🪄:"-Zeile (Abgrenzung §2.5).
- **Input-Vertrag:** `OverrideMessageResolver` bekommt **getrimmten** Text (View trimmt, `AIChatView.java:552`). Resolver: `startsWith("!")` ohne `stripLeading`.
- **Resolver-Vertrag (eindeutig):**
  - `text == null` ODER `!text.startsWith("!")` ODER `!agentWorking` ODER Rest nach `!` blank → `Optional.empty()`
  - Rest beginnt mit `/` und Resolver findet Command/Skill → `Optional.of(body + (trailing non-blank ? " " + trailing : ""))`
  - sonst → `Optional.of(rest)`
- **D1 (Entscheidung im Plan, Paul kann vetoieren, §9):** Agent working + Text = nur `!` (Rest blank) → **stilles No-Op** (View: Input clear, keine Queue, kein Turn, keine History-Zeile). Implementierung: 2-zeiliger Guard in `resolveOutgoingMessage` vor dem Resolver (`working && startsWith("!") && hasNoValue(substring(1)) → clearText + return`). Idle + `!`-alone bleibt regulärer Turn (D-idle exakt).
- **Keine Status-Flips, keine SOLL-Doku-Änderung im Plan** (Paul flippt Regel 8 nach Smoke). Kein neues ADR.
- Core-Tests: JUnit 5 + AssertJ + GIVEN/WHEN/THEN-Kommentare. Plugin-Modul: JUnit 4, keine AssertJ (hier irrelevant — I2 hat keine automatischen Tests).
- Edits: `eclipseEditFile` mit eindeutigem oldString (nie Zeilennummer), danach Zielbereich re-readen (Insert-Instabilität der Replace-Tools).
