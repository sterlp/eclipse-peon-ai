## 3. Design-Entscheidung
**Footer lebt in SkillTool, nicht in SkillPromptFile.renderBody()** — der Report-Aufruf ist ein
Tool-Response-Contract gegenüber dem LLM, kein Skill-Content; SkillServiceTest-Assertions auf
renderBody bleiben unberührt. Eine private Konstante + eine private Append-Methode decken beide
@Tool-Methoden (ein Ort, genau einmal pro Ergebnis):

```java
/** R1 skill-evolution-loop: max ~2 lines, token discipline — ask is part of the read result. */
private static final String USEFULNESS_FOOTER =
        "Report in your answer — helpful? wrong/outdated/incomplete? obsolete?";

private static String withUsefulnessFooter(String content) {
    return content + System.lineSeparator() + USEFULNESS_FOOTER;
}
```

- Englisch (Tool-Output-Konvention), eng am SOLL-Wortlaut, **eine Zeile** + Separator = im
  ~2-Zeilen-Budget.
- `System.lineSeparator()` (memory #7: Tool-Output; skillRead-Ergebnis ist ohnehin
  lineSeparator-basiert — konsistent mit renderBody, nicht mit skillLists "\n").
- Kein trailing newline → `endsWith(FOOTER)` ist deterministisch.
- **Nur Erfolgs-Pfade:** not-found-Returns (beide Methoden) bleiben ohne Footer — kein Skill
  gelesen, nichts zu reporten. `skillList` bleibt ohne Footer (Listen-Discovery, kein Read;
  R1 nennt nur skillRead/skillReadFile).

## 5. inc-1 — Usefulness-Footer auf beiden Read-Pfaden
- **Ziel:** GIVEN ein Agent liest einen Skill WHEN das Ergebnis gerendert wird THEN endet es mit
  dem Usefulness-Report-Aufruf — für skillRead UND skillReadFile, genau einmal.
- **Files:** s. Tabelle.
- **Tests** (SkillToolTest, GIVEN/WHEN/THEN-Kommentare, AssertJ):
  - `skillReadAppendsUsefulnessFooter`: GIVEN Skill-Dir mit SKILL.md + referenzierter Datei
    (Fixture wie bestehender `test`) WHEN `subject.skillRead("foo")` und
    `subject.skillReadFile("foo", "refs/bar.md")` THEN beide Ergebnisse `endsWith(FOOTER)` /
    enthalten den Report-Aufruf, je **genau einmal** (`contains` zählen oder
    `indexOf == lastIndexOf`); AND skillRead enthält weiterhin den Body.
    (Rot ohne Feature: kein Footer am Ende.)
  - AND not-found bleibt footer-frei: `subject.skillRead("missing")` endsWith **nicht** FOOTER.
  - Bestandstest `test`: skillReadFile-Assertions isEqualTo → contains + endsWith(FOOTER).

## 6. Regeln & Constraints
- Kein neues Tool, keine Prompt-Änderung (R6), keine Signature-Änderungen — @Tool-Contracts
  (Name/Params) bleiben identisch.
- Log OR throw unverändert; Footer ist reiner Text, kein onTool-Noise nötig (onTool-Zeilen
  existieren bereits).
- Test-Honesty: neuer Test ohne Feature rot (endsWith schlägt fehl); isEqualTo-Anpassung ist
  echter Contract-Wechsel (Footer ist jetzt Teil des Ergebnisses).
- Token-Disziplin: eine Footer-Zeile, keine Variationen, keine dynamischen Anteile.
