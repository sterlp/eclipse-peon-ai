## 1. Context (Warum)
IST: `ShellTool.shellRunCommand` mit fehlender `workingDirectory` läuft in `Path.of(".")` =

SOLL (`docs/shell-tool.md` § R3, ❌ specified 2026-09-24, Paul): Default = **Disk-Pfad des

## 2. Design-Entscheidungen (alle final — nichts davon neu entwerfen)
- **D1 Supplier statt eingefrorenem Feld:** `ShellTool` (core) bekommt optionalen
  `Supplier<Path> defaultWorkingDir` + Setter — exakt das `setConfirmationProvider`-Muster
  (ShellTool.java:38-45, non-volatile, wird bei Konstruktion gesetzt). SOLL-normiert
  (R3: „kein eingefrorenes Feld" — R-TC-7-Muster). Call-Zeit → Projektwechsel wirkt sofort.
- **D2 Wiring = PeonAiService-Konstruktor, NICHT `setProject()`/`SharedToolsComponent`:**
  `SharedToolsComponent` bleibt umgebungsunabhängig (keine IProject-Kenntnis); PeonAiService
  ist das Composition Root und alleiniger Erzeuger der SharedToolsComponent (IST-geprüft:
  `new ShellTool()` in Produktion nur in `ToolService`-Defaults; `BuildPoAgentComponent:67` und
  `AiScaffoldAgent:53` bauen `ToolService(false)` = ohne ShellTool → **ein einziges
  Wiring-Line deckt ALLE Produktions-Shell-Pfade**, inkl. Sub-Agenten, die den SharedService
  teilen). `setProject()`-Freezing wäre zwar möglich (Choke-Point :253), widerspricht aber
  dem SOLL (Call-Zeit-Evaluation).
- **D3 IProject→Disk-Pfad: `JdtUtil.diskPathOf(IResource)` (JdtUtil.java:194, @Nullable→String)**
  wiederverwenden — dieselbe Konversion, die `PeonAiService.setProject` :263 für alle Disk-Tools
  nutzt (Repo-Vertrag „One behaviour, one implementation"). Kein eigener
  `getLocation().toOSString()`-Code.
- **D4 Pin-Semantik ist free:** Der Pin verhindert auf View-Ebene, dass `UserContext` bei
  Selektionswechsel überschrieben wird (AIChatView:286). Der Supplier liest
  `getProject()` (= `userContext.getCurrentProject()`, volatile, UserContext:25-26) → Pin
  fließt automatisch ein. Kein extra Pin-Code, kein Pin-Test im Headless (View-Verhalten;
  via Code-Read + manueller Smoke abgedeckt).
- **D5 `cwd=`-Disclosure an 5 Return-Stellen** (nach der Validierung :89-92): Timeout,
  empty-success (stats-only), normal success, IOException, InterruptedException. Lokal
  `String cwdPrefix = "cwd=" + effectiveDir + System.lineSeparator();` — `effectiveDir` ist
  absolut + normalisiert; deckt auch explizit **relative** Pfade ehrlich ab (zeigt, worauf sie
  aufgelöst wurden). **Nicht** an der Deny-Return (:82 — Command lief nicht) und nicht an der
  Invalid-Dir-Exception (:91 — Exception-Message benennt den Pfad bereits = ehrlich).
  Format: `cwd=<absolute path>` als **erste Zeile** des Return-Strings.
- **D6 Fehlendes Projektdirectory:** Supplier prüft **nicht** Directory-Existenz; die
  bestehende Validierung :90-92 wirft `IllegalArgumentException("workingDirectory is not a
  valid directory: <pfad>")` — ehrlicher Fehler, Single-Validation-Point (D3-Prinzip).
- **D7 Kein Getter am Supplier.** Verhaltenstests (Ausführung + Output) reichen;
  Introspection-Getter = tote API.
- **D8 `@Tool`-Description von `workingDirectory` bleibt unverändert** (SOLL schweigt dazu;
  Minimal-Diff).
- Core bleibt Eclipse-frei: nur `java.util.function.Supplier` + `java.nio.file.Path`.

## 4. Rules & Constraints
- Core: null-safe (Supplier null, Supplier→null, explizit null `workingDirectory` — alle →
  `.` wie heute). Expliziter Pfad: Verhalten 1:1 unverändert, inkl. `IllegalArgumentException`
  bei ungültigem Pfad (existierender Test `runOsCommand_invalidWorkingDir_throws` bleibt grün).
- `System.lineSeparator()` in allen Output-Zusammensetzungen (Memory #7).
- Kein Logger/Throw-Doppelverstoß; keine neuen Exceptions.
- Test-Honesty (Memory #30): jede R3-Assertion muss ohne Feature **rot** sein — also Output
  (`cwd=`) UND Ausführung (gewechseltes Projekt-Verzeichnis per `pwd`) verifizieren, nicht nur
  „ein Call kam".
- Bestehende Tests bleiben **unaufgefordert grün** (`runOsCommand_nullWorkingDir_usesCurrentDir`
  = Regression-Guard für „kein Supplier → `.`").
