## 2. Inkrement 1 — Edit-Guard

### 2.1 Design

**Choke-Point `FileUtils.applyEdit`** (core, `org/sterl/llmpeon/shared/FileUtils.java`) —
Guard als **erste** Prüflinie, vor der `oldStr.equals(newStr)`-Prüfung (die bei null NPE):

```java
public static String applyEdit(String content, String oldStr, String newStr) {
    // Edit-Guard: oldString ist Pflicht-Anker, min. 3 Non-Whitespace-Zeichen.
    if (oldStr == null || oldStr.trim().length() < 3) {
        throw new IllegalArgumentException(
            "oldString is required, min 3 non-whitespace chars — use replaceLines/insertLines/writeFile for micro edits");
    }
    ...
}
```

- Message exakt wie Doc-BDD („names requirement"). `countOccurrences`-Throw bleibt als
  zweite Barrier (unberührt).
- `FileUtils.applyEdit`-Call-Sites (5, Grep-verifiziert): `diskEditFile`, `eclipseEditFile`,
  `eclipseUpdateOpenFile` (alle drei unten), `EclipseUtil.editInEditor` (L162, UI-Thread,
  IDocument-Pfad — Strings unverändert weitergereicht, bekommt den Guard gratis),
  `PlanTool.planUpdate` (hat bereits `ArgsUtil.requireNonBlank` — 2-Zeichen-Anker treffen
  ab jetzt den Guard; **gedeckte Oberfläche**, Doc-Erwähnung im Abschluss = PO-Finding).

**Oberflächen-Aufräumung** (jeweils nur, damit die Guard-Message die Einzige ist):
- `DiskFileWriteTool.diskEditFile`: **entfernen** `ArgsUtil.requireNonBlank(oldString, "oldString")`
  (sonst sieht man die BDD-Message nie) und **entfernen** die frühe
  `if (oldString.equals(newString)) throw ...`-Prüfung (NPE bei null; kein Test pinnt die
  Tool-Message). `newString == null → ""` bleibt.
- `EclipseWorkspaceWriteFileTool.eclipseEditFile` (~L110): **entfernen**
  `if (oldString == null) oldString = "";` und den Both-Null-Precheck
  „Provide a now or old string!".
- `EclipseWorkspaceWriteFileTool.eclipseUpdateOpenFile` (~L70, im `runInUiThread`-Lambda):
  **entfernen** `inOldString == null ? "" :` (null durchreichen); **behalten** den Both-Null-
  Precheck (versagt vor dem UI-Thread).
  **Bekannter IST (Out-of-Scope, PO-Finding):** alle `applyEdit`-Fehler dieses Tools werden
  von `catch (Exception e) throw new IllegalStateException("Timeout during eclipse editor read", e)`
  verpackt — veralteter Wrapper (Read liegt vorher), prä-existierend, nicht dieses Inkrement.

## 5. Regeln & Constraints

  unverändert; bestands-Pins dürfen nur dort angepasst werden, wo dieses Inkrement die
  Surface ändert (Inventare §2.3, §4.4).
- Plugin-Tests JUnit 4 ohne externe Assertion-Libs; Core JUnit 5 + AssertJ;
  GIVEN/WHEN/THEN in Testnamen/Kommentaren.
- **Kein Commit mit rotem Test.** Repro/Adaptation vor Feature in einem Inkrement:
  zuerst Adaptionen + neue Tests rot, dann Fix, dann grün — aber Commit nur im grünen Zustand.
